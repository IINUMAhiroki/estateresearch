# 既存テーブルの安全な変更（Expand/Contract）

本番にユーザーがいる前提で、1回のマイグレーションで破壊的変更をしない。列追加→バックフィル→制約強化→（リネーム/削除は）旧列除去、を**複数のマイグレーションに分割**する。GitHub/Stripe等のエンジニアリングブログで広く採用されているパターン。

個人開発でまだ実ユーザーがいない・すぐ `db reset` できる段階では、この手順を省略して1マイグレーションで直接書き換えて構わない（実際にこのプロジェクトでも過去2回、スキーマを1マイグレーションで全面書き換えしている）。**本番にユーザーが乗った後**は必ず以下の分割手順に従う。

## 列を追加する（NOT NULL にしたい場合）

1. **Expand**: 新しい列を `nullable`（または `default` 付き）で追加するマイグレーションを作る。既存のコードは新しい列を知らなくても動き続ける。
2. アプリコードを新しい列を書き込むように変更・デプロイする（新規行は必ず値が入る状態にする）。
3. 既存行をバックフィルする（`update` 文、または別マイグレーションのデータ移行）。
4. **Contract**: 全行に値が入ったことを確認してから、別マイグレーションで `alter table ... alter column ... set not null` する。

## 列をリネームする

1. **Expand**: 新しい列名で列を追加し、旧列と同じ値を書き込むトリガー（または両方に書くようアプリを変更）を用意する。
2. アプリコードを新しい列名を読むように切り替える。
3. **Contract**: 十分な移行期間の後、別マイグレーションで旧列・トリガーを `drop` する。

## テーブル/列を削除する

1. アプリコードからその列・テーブルへの参照を先に全て消す。
2. デプロイして問題がないことを確認してから、別マイグレーションで実際に `drop` する。
3. 同じマイグレーション内で「参照を消す」と「dropする」を同時にやらない（ロールバックできなくなる）。

## 型を変更する（例: text → uuid）

1. 新しい型の列を別名で追加（Expand）。
2. 両方の列に書き込みつつ、旧列から新列へバックフィル。
3. 読み取りを新列に切り替え。
4. 旧列を `drop`（Contract）。

## この手順を使わなくていいとき

- ローカル/開発専用で、まだ本番ユーザーがいない（`supabase db reset` で全て作り直せる）
- 追加するだけで既存の read/write パスに影響しない列追加（nullable、default あり）

## 共通ルール（`/new-table` と同じ）

- 新しい列・テーブルにも RLS ポリシーを忘れない（テーブル自体は既存でも、列追加だけならポリシー変更は通常不要）。
- 各段階ごとに `pnpm db:reset && pnpm check:rls && pnpm db:test && pnpm db:types` を実行してから次の段階に進む。
- 段階を分けたら、それぞれ別コミット・可能なら別PRにする。
